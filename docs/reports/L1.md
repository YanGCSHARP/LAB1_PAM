## 2. Описание продукта

WalletMate — приложение для учёта личных финансов. Пользователь заводит несколько
счетов (карта, наличные, сбережения), записывает доходы и расходы с привязкой к
категории и счёту, ставит месячные лимиты по категориям и видит на общей панели,
как распределились траты и где лимит близок к исчерпанию.

Продукт отвечает на один конкретный вопрос: **«куда делись деньги в этом месяце?»**.
Всё остальное — способы дать на него ответ быстрее.

---

## 3. Обоснование выбора темы

**Задача понятна и проверяема.** Правильность работы приложения видно невооружённым
глазом: добавил расход — баланс счёта уменьшился, прогресс бюджета вырос, доля
категории на диаграмме изменилась. Это удобно и для разработки, и для защиты.

**Тема естественно покрывает все техники курса** — без искусственных «прикручиваний»:

| Техника курса | Где нужна в WalletMate |
|---|---|
| Материальный UI, тёмная тема, адаптивность | 8 экранов, карточки счетов, диаграммы |
| Навигация со вложенными маршрутами | 4 вкладки + дочерние экраны деталей и форм |
| Формы и валидация | Транзакция, счёт, бюджет, регистрация — у каждой формы свои правила |
| Управление состоянием | Один добавленный расход меняет сразу 4 экрана |
| Repository и слоистая архитектура | Mock на L4 подменяется на REST на L5 без правки UI |
| REST + аутентификация | Свой .NET backend, JWT, доступ только к своим данным |
| Локальное хранилище | Финансы вводят в дороге, где связи может не быть → offline-first |
| Работа с файлами | Загрузка аватара |
| Графики | Структура расходов по категориям |

**Есть нетривиальная бизнес-логика.** Балансы и прогресс бюджетов — не хранимые поля,
а агрегаты, которые надо считать одинаково на клиенте (mock-этапы) и на сервере,
с корректной обработкой границ (89.9 % / 90 % / 100 %) и денежной арифметики
(`decimal`, два знака, никаких строковых сложений).

**Личный интерес.** Тема решает реальную задачу автора и используемых им сценариев,
а значит, требования проверяются на собственном опыте, а не придумываются.

## 4. Целевая аудитория

**Основная:** студенты и молодые специалисты 18–27 лет, Республика Молдова.

Характерная ситуация: доход нерегулярный (стипендия, подработка, перевод от родных),
сумм немного, но контроль нужен — деньги «растворяются» на еде, транспорте и мелких
покупках. Дорогая подписка на финансовый сервис для этой аудитории неуместна,
банковское приложение показывает операции только одного банка и не видит наличных.

**Сценарии использования**

1. **Быстрая запись расхода.** Заплатил за обед — за 10–15 секунд внёс сумму,
   категорию и счёт, не выходя из очереди.
2. **Проверка лимита.** Перед покупкой посмотрел, сколько осталось в бюджете
   на категорию «развлечения» в этом месяце.
3. **Разбор месяца.** В конце месяца открыл панель и увидел, какие три категории
   съели большую часть бюджета.
4. **Учёт наличных.** Снял деньги с карты — перевёл на счёт «Наличные»,
   дальнейшие траты пишет туда.

**Требования, вытекающие из аудитории:** мультивалютность (MDL как основная, EUR и USD
для сбережений), работа без интернета, ввод расхода в минимальное число касаний,
русскоязычный интерфейс с заделом на румынский и английский.

## 5. Аналоги и отличия

Для сравнения взяты два популярных приложения того же класса, доступных в Google Play.

### Money Manager (Realbyte)

Сильные стороны: очень быстрый ввод операции, календарное представление, подробная
статистика, работает офлайн.

Слабые стороны для нашей аудитории: интерфейс перегружен — множество вкладок и
настроек, в которых новичок теряется; часть функций (резервное копирование,
расширенные отчёты) в платной версии; синхронизации между устройствами в бесплатной
версии по сути нет.

### Wallet by BudgetBakers

Сильные стороны: облачная синхронизация, бюджеты, богатая аналитика, автоматический
импорт банковских операций для ряда стран.

Слабые стороны для нашей аудитории: ключевые возможности (в том числе банковская
синхронизация и часть бюджетов) в подписке; для Молдовы автоматический импорт
фактически не работает, то есть за деньги остаётся тот же ручной ввод; приложение
тяжёлое и требует регистрации в облаке провайдера.

### Чем отличается WalletMate

| Аспект | WalletMate |
|---|---|
| Объём функций | Сознательно узкий: счета, транзакции, бюджеты, панель. Ничего, что не отвечает на вопрос «куда делись деньги» |
| Данные пользователя | Собственный backend: данные лежат там, где их разместил владелец приложения, а не у стороннего сервиса |
| Бюджеты | Порог предупреждения (≥ 90 % — жёлтый, ≥ 100 % — красный) вынесен прямо на главный экран, а не спрятан в отчёты |
| Офлайн | Не «режим только для чтения», а полноценная работа: запись уходит в очередь и синхронизируется при появлении сети |
| Монетизация | Учебный проект, платных функций нет; весь набор доступен сразу |
| Локальный контекст | MDL по умолчанию, категории и суммы под молдавские реалии, русский интерфейс с заделом на RO/EN |

Сравнение основано на публично доступном описании приложений в магазине и их
бесплатных версиях; точные наборы платных функций у обоих продуктов со временем
меняются.

## 6. Оценка сложности

Тема заявлена на уровень «повышенная». Ниже — что именно выводит её за пределы
минимального CRUD-приложения.

| Функция | Почему это повышенный уровень |
|---|---|
| Собственный .NET backend | Не подключение готового API, а проектирование сущностей, миграций, контроллеров и тестов |
| JWT-аутентификация | Хэширование паролей, выдача и проверка токена, хранение в `flutter_secure_storage`, interceptor и auth-guard в роутере |
| Изоляция данных пользователей | Каждый запрос фильтруется по `userId` из токена; запрет доступа к чужим записям проверяется интеграционным тестом |
| Серверные агрегаты | `/dashboard/summary` и `progress` бюджетов считаются на сервере — SQL-группировки, а не выборка «всего подряд» |
| Фильтры и пагинация | 7 параметров фильтрации транзакций, серверная пагинация, подгрузка при скролле |
| Графики | Кольцевая диаграмма структуры расходов с легендой и долями (`fl_chart`) |
| Загрузка файла | Аватар: multipart, ограничение типа и размера, раздача через статику |
| Offline-first | Локальная БД `drift`, очередь `pending_operations`, проигрывание очереди с экспоненциальным backoff, замена временных id на серверные, стратегия конфликтов last-write-wins |
| Слоистая архитектура | Repository + провайдеры: на L5 mock меняется на REST без единой правки в экранах — абстракция проверяется на прочность |
| Тестирование | Unit (валидаторы, агрегаты, мапперы), repository-тесты, widget-тесты, `integration_test` сквозного сценария, интеграционные тесты backend-а |
| Release и CI | Подпись APK, обфускация, иконка и сплэш, GitHub Actions на анализ/тесты и сборку по тегу |

## 7. Объём работ по этапам

| Этап | Содержание | Ориентировочный объём |
|---|---|---|
| L1 | Спецификация, ER-модель, карта экранов, контракт API, скелет репозитория | выполнено |
| L2 | 8 статических экранов на Material 3, темы, mock-данные, общие виджеты | ~2 дня |
| L3 | `go_router` со вложенными вкладками, валидация всех форм, unit-тесты валидаторов | ~1,5 дня |
| L4 | Riverpod, доменные модели, репозитории на mock-данных, производные агрегаты, состояния loading/error/empty | ~2,5 дня |
| L5 | .NET Web API (сущности, миграции, JWT, CRUD, агрегаты, тесты) + интеграция клиента по REST | ~4 дня, в два подхода |
| L6 | `drift`, очередь синхронизации, полный набор тестов, release-сборка, CI, финальная документация | ~3 дня |

## 9. Принятые решения и их обоснование

| Решение | Почему |
|---|---|
| Riverpod вместо Bloc/Provider | Меньше шаблонного кода, производные провайдеры-агрегаты выражаются естественно; при требовании преподавателя заменяется только слой L4, архитектура не меняется |
| Балансы и прогресс — вычисляемые, не хранимые | Исключает рассинхронизацию данных: одна транзакция не может «забыть» обновить баланс |
| `Transaction` без поля `userId` | Владелец однозначно определяется через счёт; дублирование ссылки создало бы риск расхождения |
| Агрегат `/dashboard/summary` на сервере | Клиенту не нужно тянуть все транзакции месяца ради диаграммы; экономия трафика и одинаковый результат на всех устройствах |
| Ключи категорий на английском | Подписи берутся из ARB-файлов; добавление RO/EN не требует миграции данных |
| SQLite для разработки, PostgreSQL в Docker для демо | Быстрый старт без инфраструктуры, но демонстрация на «взрослой» БД |

## 10. Риски и открытые вопросы

| Вопрос | Статус |
|---|---|
| Выдаст ли преподаватель .NET-шаблон курса | Если да — backend строится на его основе, добавляются только свои сущности; уточнить до начала L5 |
| Требуется ли Bloc вместо Riverpod | Уточнить до начала L4; переписывается только слой состояния |
| Мультивалютность | На L2–L6 счета в разных валютах не приводятся к одной; конвертация вынесена в бонусное задание |
| Объём L5 | Самый тяжёлый этап; делится на два подхода (backend, затем интеграция), чтобы не получить один гигантский коммит |
| Устройство для демонстрации release-сборки | Нужен физический Android или эмулятор с достаточной памятью для `--split-per-abi` |
