# Отчёт по лабораторной работе L3

**Дисциплина:** Программирование мобильных приложений (PAM), UTM / FCIM / ISA
**Тема:** T7 — WalletMate (личные финансы), уровень сложности «повышенный»
**Автор:** Yang Alexandru, группа `TI-236`
**Этап:** L3 — навигация на `go_router` и формы с валидацией
**Дата:** октябрь 2026

---

## 1. Цель этапа

Связать статические экраны L2 в единое приложение с декларативной навигацией:
у каждого экрана есть свой URL, вкладки сохраняют состояние, закрытые разделы
недоступны без входа. Все формы проверяют ввод по правилам из модели данных
(`docs/er-diagram.md`) и контракта API (`docs/api-contract.md`), а правила покрыты
unit-тестами.

Данные на этом этапе по-прежнему демонстрационные (mock): сохранение в форме
закрывает экран и показывает `SnackBar`, но список не меняется. Хранение появится
на L4 вместе с репозиториями.

---

## 2. Что сделано

| Требование L3 (из плана L1) | Реализация |
|---|---|
| `go_router` со вложенными вкладками | `StatefulShellRoute.indexedStack` с четырьмя ветками: Панель, Транзакции, Бюджеты, Профиль |
| Маршруты для всех 8 экранов | Дерево в `core/router/app_router.dart`, пути — в `core/router/app_routes.dart` |
| Экран ошибки маршрутизации | `errorBuilder` → `NotFoundScreen`; тот же экран показывается для несуществующего `id` |
| Защита закрытых маршрутов | `redirect` по флагу сессии (`AuthSession`) |
| Валидация всех форм | Вход, регистрация, транзакция, бюджет, счёт — правила в `core/validation/validators.dart` |
| Unit-тесты валидаторов | `test/unit/validators_test.dart` — 35 тестов |

Сверх плана:

- фильтры списка транзакций хранятся в query-параметрах URL;
- выход из изменённой формы требует подтверждения (`UnsavedChangesGuard`);
- проверки уникальности: имя счёта, бюджет на категорию и месяц;
- widget-тесты навигации и вёрстки всех экранов на ширине 360 px.

## 3. Навигация

### 3.1. Дерево маршрутов

```
/login                       вход
/register                    регистрация
StatefulShellRoute (вкладки, нижняя панель)
├── /dashboard               Панель
├── /transactions            список (?type, ?category, ?month, ?q)
│   ├── new                  форма создания            [корневой навигатор]
│   └── :id                  карточка транзакции
│       └── edit             форма редактирования      [корневой навигатор]
├── /budgets                 бюджеты (?month)
│   ├── new                  форма бюджета             [корневой навигатор]
│   └── :id/edit             редактирование бюджета    [корневой навигатор]
└── /profile                 Профиль
/accounts                    Мои счета (вне вкладок)
├── new
└── :id/edit
```

### 3.2. Решения по навигации

**Вкладки — `StatefulShellRoute.indexedStack`.** У каждой вкладки свой навигационный
стек: если открыть карточку транзакции, перейти на «Бюджеты» и вернуться, карточка
остаётся открытой, позиция прокрутки тоже сохраняется.

**Формы — на корневом навигаторе** (`parentNavigatorKey: rootKey`). Форма перекрывает
нижнюю панель, поэтому наполовину заполненную форму нельзя случайно бросить одним
нажатием на соседнюю вкладку.

**Счета — вне оболочки.** На экран счетов ведут две вкладки: Панель (карточка счёта)
и Профиль («Мои счета»). Маршрут лежит на верхнем уровне и открывается поверх той
вкладки, из которой его вызвали; «Назад» возвращает на неё.

**`new` объявлен раньше `:id`.** Иначе `/transactions/new` распознаётся как
транзакция с идентификатором `new`.

**Пути только через `AppRoutes`.** Экраны не пишут строки путей вручную, а вызывают
`AppRoutes.transaction(id)`, `AppRoutes.budgetNew(month: …)` и т. д. Опечатка в пути
становится ошибкой компиляции, а не 404 во время работы.

### 3.3. Фильтры в URL

Фильтры списка транзакций — часть адреса, а не состояние виджета:

```
/transactions?type=expense&category=food&month=2026-09&q=кофе
```

За разбор и сборку отвечает `TransactionFilter` (`fromQuery` / `toQuery`). Это даёт:

- сектор диаграммы на Панели и строка бюджета открывают уже отфильтрованный список
  обычной ссылкой;
- кнопка «Назад» восстанавливает предыдущий набор фильтров;
- некорректные значения в ручной ссылке (неизвестный тип, месяц `2026-13`)
  отбрасываются, а не ломают экран.

### 3.4. Auth-redirect

Логика вынесена в чистую функцию `authRedirect(signedIn, location)`, поэтому
тестируется без виджетов:

| Состояние | Куда идёт пользователь | Результат |
|---|---|---|
| Не вошёл | закрытый маршрут (`/dashboard`, `/transactions/t1`, …) | → `/login` |
| Не вошёл | `/login`, `/register` | остаётся |
| Вошёл | `/login`, `/register` | → `/dashboard` |
| Вошёл | любой закрытый маршрут | остаётся |

Роутер подписан на сессию (`refreshListenable: session`): вход и выход сразу
перезапускают redirect. Последнее правило таблицы не даёт кнопке «Назад» вернуть
на форму входа после успешного входа.

На L3 сессия — флаг в памяти. На L5 класс `AuthSession` начнёт хранить JWT в
защищённом хранилище; роутер и экраны при этом не меняются.

## 4. Валидация форм

### 4.1. Правила

Все правила собраны в одном классе `Validators` и повторяют ограничения модели данных.

| Поле | Правило | Сообщение об ошибке (пример) |
|---|---|---|
| Email | обязателен, формат `x@y.zz`, ≤ 254 символов, пробелы по краям обрезаются | «Неверный формат email, например you@example.com» |
| Пароль при входе | только обязательность | «Введите пароль» |
| Пароль при регистрации | ≥ 8 символов, хотя бы одна буква (латиница или кириллица) и одна цифра, без пробелов | «Нужны хотя бы одна буква и одна цифра» |
| Подтверждение пароля | точное совпадение | «Пароли не совпадают» |
| Имя | 1–100 символов | «Не длиннее 100 символов» |
| Название счёта | 1–50 символов, уникально без учёта регистра | «Счёт с таким названием уже есть» |
| Начальный баланс | необязателен, может быть отрицательным (кредитная карта) | — |
| Сумма транзакции | > 0, ≤ 1 000 000, не больше двух знаков после запятой; принимаются `1 234,56` и `1234.56` | «Сумма должна быть больше нуля» |
| Лимит бюджета | те же правила, что у суммы | «Лимит должен быть больше нуля» |
| Заметка | необязательна, ≤ 200 символов | «Не длиннее 200 символов» |
| Категория, счёт, месяц | обязательный выбор | «Выберите категорию» |
| Дата транзакции | обязательна, не позже завтрашнего дня | «Дата не может быть позже завтрашнего дня» |
| Бюджет | один на пару «категория + месяц» | «На этот месяц бюджет по категории уже есть» |

### 4.2. Поведение форм

- **Вход и регистрация** показывают ошибки после первой попытки отправки, а дальше
  обновляют их при вводе. Пустая форма, которая сразу краснеет, раздражает.
- **Формы транзакции, бюджета и счёта** проверяют поле, как только пользователь его
  тронул (`AutovalidateMode.onUserInteraction`). Кнопка «Сохранить» неактивна, пока
  форма невалидна.
- **Пароль при входе** проверяется только на заполненность. Если повторять там
  требования к сложности, постороннему будет видна парольная политика.
- **Знак суммы** задаёт переключатель «доход / расход», а не минус. При смене типа
  сбрасывается категория, которая к новому типу не подходит.
- **Защита от потери ввода.** Если форма изменена, жест «назад» и стрелка в
  `AppBar` открывают диалог «Выйти без сохранения?». Нетронутая форма закрывается
  сразу, а сохранение закрывает экран в обход диалога.
- **Удаление** транзакции, счёта и бюджета, а также выход из аккаунта проходят через
  диалог подтверждения. Закрытие диалога тапом мимо считается отказом.

## 7. Принятые решения и их обоснование

| Решение | Почему |
|---|---|
| `go_router`, а не `Navigator 2.0` вручную | Официальный пакет команды Flutter; вложенные вкладки, redirect и deep links из коробки |
| `indexedStack`-оболочка | Вкладки не пересоздаются при переключении, состояние и прокрутка сохраняются |
| Формы на корневом навигаторе | Нельзя переключить вкладку посреди заполнения формы |
| Фильтры в URL | Ссылки с Панели и из бюджетов ведут сразу в нужную выборку, «Назад» работает естественно |
| `authRedirect` — чистая функция | Логика доступа тестируется unit-тестами без запуска виджетов |
| Все валидаторы в одном классе | Одно место для правил; при подключении backend-а на L5 их легко сверить с серверной валидацией |
| Ошибки на русском, тексты — в `AppStrings` | Интерфейс целиком на русском; перевод на RO/EN не затронет логику |

## 8. Ограничения и что дальше

| Ограничение | Когда снимается |
|---|---|
| Сохранение и удаление не меняют данные — только закрывают экран и показывают `SnackBar` | L4: репозитории на mock-данных и Riverpod |
| Сессия — флаг в памяти, после перезагрузки нужно входить заново | L5: JWT и защищённое хранилище |
| Тема приложения не сохраняется между запусками | L4: переходит в слой состояния |
| Уникальность счёта и бюджета проверяется только по mock-списку | L5: дублируется серверной проверкой (409 Conflict) |

Следующий этап — **L4**: доменные модели, репозитории на mock-данных, Riverpod,
производные агрегаты (балансы, прогресс бюджетов) и состояния loading / error / empty.
